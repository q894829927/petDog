# 倩岚汪 — 技术设计文档

- 文档版本：0.2
- 状态：前端原型与账号存档 API 已实现
- 目标：支持 3D 宠物互动、账号系统、跨设备云端存档和按现实时间结算的宠物状态

## 当前 UI 设计基线

2026-11 确定 [Warm Flat 全屏 HUD 规范](UI_DESIGN_BASELINE.md)。R3F 房间通过 `useFrame` 更新动作，Zustand 管理低频界面状态和云端快照。访客看到演示数值，已领养的账号显示 API 返回的宠物状态。

## 1. 总体架构

采用前后端分离的单仓库结构。前端是静态 Web 应用，后端是独立 Node.js 服务，数据库存放在 ECS 的持久化目录。

浏览器
  ├── Vite + React + Three.js
  └── 同源请求 /pet-api/v1/*
          |
          v
      Nginx 反向代理
          |
          v
      Fastify API（127.0.0.1:3180）
          |
          v
      SQLite（持久化文件）

前端部署在 Game-Portal 的 /games/petdog/。API 使用同域 /pet-api/ 路径，避免跨域 Cookie 和 CORS 配置复杂度。

## 2. 技术选型

### 前端

- Vite：开发服务器与生产构建。
- React + TypeScript：界面和应用结构。
- Three.js：3D 渲染基础。
- React Three Fiber：在 React 中组织 3D 场景。
- GLTFLoader 与 AnimationMixer：加载和混合宠物骨骼动画。
- Zustand：本地交互状态、场景状态和 UI 状态。
- Fetch：同源 API 请求、重回页面同步和动作保存队列。

### 后端

- Node.js 22.18+ 与 TypeScript。
- Fastify：HTTP API。
- SQLite：Node.js 内置驱动、参数化语句和版本化 SQL 迁移。
- Argon2id：密码哈希。
- Fastify JSON Schema：输入验证。
- Node.js 测试运行器：认证、并发、事务、离线时间和持久化验证。

SQLite 适合当前单服、低频宠物互动和读多写少的规模。数据库文件放在仓库之外，使用 WAL 模式、短事务和备份策略。未来需要多实例部署或高并发写入时，再迁移 PostgreSQL。

## 3. 仓库结构

- shared：前后端共用的类型和常量。

## 4. 前端模块

### 4.1 场景层

- LivingRoom：客厅、照料摆设和灯光。活动边界与关键摆设位置由场景和导航共同使用。
- BreedCatalog：可用犬种定义与资源清单。
- PetModel：按犬种配置加载 GLB 模型。
- PetRigAdapter：将各犬种骨骼映射到统一语义骨骼接口。
- BreedAnimationProfile：将统一动作语义映射到犬种动画片段。
- PetAnimator：动画状态与动画混合。
- PetNavigation：房间内有限区域移动。
- InteractionRaycaster：鼠标与触摸命中检测。
- StageCamera：近场取景随团子缓慢移动。远抛时根据团子和球的位置平滑拓宽取景，追球结束回到近场。手势按住期间保持机位。

客厅的墙、窗框、地毯、碗和狗窝由场景几何构成。地板和窗景贴图随静态包发布，三个 WebP 合计约 102 KB。

- 浅木地板采用 ambientCG 的 Wood Floor 066 A。基色贴图为 1024×1024，法线贴图为 512×512，高画质启用地板法线。 [资产](https://ambientcg.com/view?id=WoodFloor066A) · [CC0](https://docs.ambientcg.com/license/)
- 窗外取自 Andreas Mischok 在 Poly Haven 发布的 Greenwich Park 02，从 1K HDRI 投影为 960×448 的窗景。 [资产](https://polyhaven.com/a/greenwich_park_02) · [CC0](https://polyhaven.com/license)
- 木地板和地毯共用同一个接触平面。两档画质都绘制摆件、犬和球的柔和接触阴影，球离地后接触阴影淡出。标准画质还会渲染主光投影。

### 4.2 宠物行为表现

前端负责把服务端状态和当前交互转化为实时画面：

- 服务端状态决定宠物需求、心情和持久化个体数据。
- 本地行为控制器根据需求、环境、犬种倾向和个体性格选择短时行为。
- 通用行为只使用统一语义动作；犬种适配层负责映射到实际动画片段和骨骼。
- 本地表现层负责动画衔接、路径插值、触摸部位反馈和犬种专属动作。
- 动画播放完成、转场和动作打断由本地表现层管理。
- 客户端可以预测动画反馈，但不能自行确认饱腹、物品数量或亲密度等持久数据。

### 4.3 UI 层

- Auth：注册、登录。
- PetHUD：名字、年龄、状态。
- InteractionBar：呼唤、饮食、梳毛。玩家在 3D 房间中直接抚摸宠物和抓球。
- Inventory：食物和玩具。
- PetProfile：性格、年龄、亲密度。
- SyncIndicator：保存中、已同步、同步失败。

## 5. 后端模块

- auth：注册、登录、退出、当前会话。
- pet：宠物创建、档案、状态读取。
- simulation：根据服务器时间结算自然变化。
- interaction：处理抚摸、喂食、喝水、玩耍和清洁。
- persistence：数据库访问和事务。
- health：服务健康检查。

业务模块不直接读取客户端时间。所有影响持久数据的操作都通过服务端事务执行。

## 6. 数据模型

### users

- id：主键。
- email：唯一登录邮箱。
- password_hash：Argon2id 哈希。
- created_at：创建时间。

### sessions

- token_hash：主键，Session 随机令牌的哈希值。
- user_id：所属用户。
- expires_at：过期时间。

数据库只保存 Session 令牌哈希，不保存浏览器 Cookie 中的原始令牌。

### pets

- id：主键。
- user_id：唯一外键，一个账号首版只拥有一只宠物。
- name：宠物名字。
- breed_id：目标犬种标识，对应客户端或服务端维护的可用犬种目录；当前 001_initial.sql 尚未包含该字段，启用犬种选择时通过新增版本化迁移加入。
- personality：个体性格配置，与犬种默认行为倾向分开保存。
- adopted_at：领养时间。
- hunger：饱腹值。
- hydration：水分值。
- energy：精力值。
- cleanliness：清洁度。
- happiness：心情值。
- affection：亲密度。
- sleeping：睡眠状态。
- last_simulated_at：上次结算时间。
- version：乐观并发版本号。

### pet_actions

- pet_id：所属宠物。
- request_id：客户端生成的幂等请求 ID，对宠物唯一。
- action：互动类型。
- result：首次提交成功后的宠物快照。
- created_at：服务端记录时间。

互动日志用于幂等处理、排查问题和后续行为统计，不记录不必要的个人信息。

## 7. 宠物时间模拟

### 7.1 结算原则

每只宠物记录 last_simulated_at。读取宠物或执行互动时：

1. 开启数据库写事务。
2. 锁定或保护当前宠物记录，读取最新状态。
3. 使用服务端当前 UTC 时间减去 last_simulated_at，得到 elapsedSeconds。
4. 根据经过时间、睡眠状态和性格参数结算需求变化。
5. 将数值限制在 0—100。
6. 更新 last_simulated_at 和 version。
7. 提交事务并返回权威状态。

SQLite 使用短写事务，例如 BEGIN IMMEDIATE，避免两个设备同时结算同一只宠物时发生丢失更新。

### 7.2 状态规则

- 饱腹和水分随时间下降。
- 清洁度缓慢下降。
- 清醒时精力下降，睡眠时精力恢复。
- 心情受需求状态和互动影响。
- 亲密度通过有效的正向互动增加，不因离线时间下降。
- 年龄通过 adopted_at 与服务端当前时间计算。
- 所有状态值限制在 0—100。
- 不设计死亡或永久损失。

具体速率集中定义在 `apps/api/src/simulation.ts`。结算使用服务端记录的经过时长直接计算，睡眠时恢复精力。当精力低于 25 时，房间里的宠物更早回到狗窝休息。

### 7.3 交互结算

互动请求必须先结算自然变化，再校验动作条件，最后应用动作效果并保存。

例如喂食：
1. 结算离线和当前自然变化。
2. 验证领养状态、动作类型、请求 ID 和宠物版本。
3. 恢复饱腹值并更新心情。
4. 更新宠物版本并写入 pet_actions，保存在同一事务中。
5. 返回服务端宠物快照。

同一个 request_id 重试时返回第一次执行结果。当前饮食托盘提供可随时补充的标准狗粮和清水。

## 8. 并发与跨设备同步

- 所有设备访问同一服务端宠物记录。
- 每次成功写入使 version 加一。
- 互动请求携带 expectedVersion 和 requestId。
- 版本冲突时服务端返回最新状态，客户端刷新后再决定是否重试。
- 前端在页面恢复焦点时重新获取宠物状态。读取和写入携带当前账号 ID，Cookie 对应账号变化时返回冲突并提示重新同步。
- 游戏运行期间以 30—60 秒低频刷新作为兜底；互动完成后立即更新。
- 首版不使用 WebSocket。只有需要实时双设备观战或即时同步时再引入。

## 9. API 设计

统一前缀：/pet-api/v1

### 认证

- POST /auth/register：注册。
- POST /auth/login：登录。
- POST /auth/logout：退出。
- GET /auth/me：获取当前用户。

### 宠物

- GET /breeds：获取当前开放的犬种目录（规划接口，按实际接入阶段实现）。
- POST /pet：现有首次创建宠物接口；多犬种功能启用后扩展 breedId、名字和个体性格，服务端校验 breedId 是否开放。
- GET /pet：获取并结算宠物状态。
- PATCH /pet/profile：修改允许编辑的档案字段。
- POST /pet/actions：提交互动动作。

互动请求示例字段：

- requestId：幂等请求 ID。
- expectedVersion：客户端已知宠物版本。
- action：pet、feed、drink、play、brush、sleep、wake、call。

服务端返回宠物快照和新版本号。客户端在完成吃喝、叼回和有效梳毛后提交对应动作。

### 健康检查

- GET /pet-api/healthz：返回服务健康状态。

## 10. 身份认证与安全

- 密码至少 6 个字符，支持纯数字密码。密码以 Argon2id 哈希保存。
- Session 使用密码学安全随机数生成，数据库只保存令牌哈希。
- Cookie 使用 HttpOnly、Secure、SameSite=Lax。
- 修改数据的请求校验 Origin，并限制请求来源。
- 登录和注册接口增加速率限制。
- 所有输入通过 Schema 校验，数据库查询使用参数化接口。
- 生产环境密钥放在 ECS 的独立环境文件中，不进入 Git。
- 账号数据、宠物存档和数据库备份不进入静态 dist。
- API 仅监听 127.0.0.1，不直接暴露公网端口。

邮箱验证、找回密码和邮件服务在正式公开注册前补齐；开发阶段可以使用受控的测试账号流程。

## 11. 3D 资源与动画要求

每个可领养犬种都需要一套经过适配的 GLB 资源。通用玩法不直接依赖某一种犬的骨骼名称或原始动画名称，而是通过犬种配置将模型资源映射到统一的动作语义和身体区域。

基础动作语义至少覆盖：

- Idle：自然待机。
- Walk：行走。
- Run：奔跑。
- Sit：坐下。
- Lie：趴下。
- Sleep：睡眠。
- LookAround：观察。
- Sniff：嗅闻。
- Eat：进食。
- Drink：喝水。
- Happy：开心反应。
- TailWag：摇尾。
- PetHead：头部被抚摸时的反应。
- PetBack：背部被抚摸时的反应。
- Bark：吠叫或回应。

动画应允许合理混合，例如尾巴动作与待机动作叠加。若模型没有独立表情骨骼，首版使用头部、耳朵、身体姿态和音效表达情绪。

模型交付需要检查骨骼命名、根骨骼方向、动作循环、动画时长、材质贴图和 GLB 文件体积。

### 11.1 多犬种适配架构

#### 设计目标

- 通用互动系统只表达“做什么”，不决定某个犬种具体播放哪个动画片段。
- 犬种配置负责说明“这个犬种如何表现”，包括模型、骨骼、动画、触摸区域、体型和行为倾向。
- 犬种专属动作作为扩展能力注册，不要求所有犬种都拥有完全相同的动画数量。
- 新增犬种时优先新增资源和配置；只有新增了通用系统尚不支持的行为能力时，才扩展公共接口。

#### 犬种定义（BreedDefinition）

每个犬种需要一份独立定义，至少包含：

| 配置组 | 字段与用途 |
|---|---|
| 身份 | breedId、显示名称、犬种介绍、缩略图 |
| 模型 | 高低画质 GLB、资源版本、默认材质、缩放和朝向修正 |
| 骨骼 | 统一语义骨骼到模型实际骨骼名称的映射，标记可选骨骼 |
| 动画 | 统一动作语义到 GLB 动画片段的映射、循环方式、播放速度和转场参数 |
| 触摸 | 头、耳、脸颊、下巴、背、腹、四肢、尾巴等语义区域及左右/前后区分 |
| 体型 | 身高、身长、碰撞范围、脚底高度、步幅、转向速度和寻路安全距离 |
| 声音 | 吠叫、呜咽、喘气、开心和不满等声音资源 |
| 行为 | 犬种默认活动倾向、探索偏好、玩具偏好和互动反应权重 |
| 专属能力 | 该犬种独有的动作、反应或互动表现，以及对应的能力标识 |

#### 统一动作语义

公共行为系统使用稳定的语义动作，例如：

- Locomotion：Idle、Walk、Run、Turn。
- Posture：Sit、LieDown、StandUp、Sleep、Stretch。
- Attention：LookAround、LookAtPlayer、Listen、Sniff。
- Care：Eat、Drink、Brush、Bath、Dry。
- Play：Chase、Reach、PickUp、Carry、Drop、Tug、Catch。
- Social：Approach、PetReaction、Happy、Relax、Bark。
- Training：Come、Stay、Paw、Spin 等已支持指令。

各犬种把这些语义动作映射到自己的动画片段。某个犬种缺少独立片段时，按优先级使用同类通用片段、程序化姿态或安全的静态表现；不能因为某个片段缺失导致整个犬种无法进入场景。对会明显破坏动作质量的关键动作，资源验收阶段必须补齐，不以回退代替正式制作。

犬种专属动作放入扩展动作表，例如特定犬种的独特坐姿、翻滚方式、尾巴动作或玩具互动。公共系统通过能力标识判断是否可以触发，不在通用组件中写犬种名称分支。

#### 统一骨骼与触摸语义

适配层建立统一语义骨骼，如 Root、Pelvis、Spine、Neck、Head、Jaw、EarLeft、EarRight、TailRoot、TailTip，以及四肢的肩/髋、肘/膝和爪部。不同模型可以缺少部分骨骼；配置明确标记必需项和可选项，并提供替代挂点。

触摸检测输出统一身体区域，而不是暴露模型内部骨骼名称。公共互动层接收 Head、Ear、Cheek、Chin、Back、Flank、Belly、Leg、Paw、Tail 等语义区域。犬种配置负责将模型表面命中点、蒙皮权重或专用碰撞区转换成这些语义区域。

每种犬都要校准身体区域边界、左右/前后判定、手部贴合距离和碰撞范围。体型差异必须进入场景导航和手部避穿检测参数，不能继续沿用秋田犬的固定缩放与安全距离。

#### 动画与表现层

- PetAnimator 只接收语义动作和参数，由 BreedAnimationProfile 查找实际片段。
- 动作缺失、骨骼缺失和转场不兼容在加载阶段报告，避免在玩家互动时才暴露。
- 尾巴、耳朵、头部等局部反应可以作为叠加层，与行走或待机动作混合。
- 每个犬种可以定义自己的独特表情、动作和音效；公共行为状态机只决定触发时机。
- 画质等级由犬种资源目录提供对应模型，动作语义保持一致。
- 动画根运动或程序化位移必须统一速度单位，并在犬种配置中校准步幅、播放速率和转向速度。

#### 当前代码与迁移顺序

当前 AkitaDog.tsx、petTouch.ts、petReactions.ts 和 roomNavigation.ts 仍包含秋田犬专属的骨骼名称、动画片段名称、缩放、步幅和触摸几何假设。现有功能可作为第一套犬种适配器的行为基准，不能视为多犬种适配层已经完成。

建议迁移顺序：

1. 固化当前秋田犬的模型、动作、骨骼、触摸区域和导航参数清单。
2. 定义 BreedDefinition、语义动作和语义骨骼映射。
3. 把当前秋田犬资源整理为 AkitaBreedProfile，保持现有交互行为回归通过。
4. 将触摸区域和体型参数从通用组件中移出。
5. 将行为控制器改为调用语义动作。
6. 接入第二犬种，使用同一套互动验收清单验证复用程度。

### 11.2 当前秋田犬原型

默认的「标准」画质使用 Dogs_Big_pack 的 `Mesh_Akita` 和材质 `M_Akita_color`。「省电」画质使用 `Mesh_Akita_LowPoly` 和材质 `M_Akita_color_M`。两档从 Unreal glTF Exporter 的原始导出分别压缩为内嵌 WebP 贴图和 Meshopt 几何、动画的 GLB，保留 7,918 / 1,872 个三角形及同一组 13 个骨骼动画。标准档的基色和法线贴图分别为 1536 和 1024 像素，省电档均为 512 像素。

`useAkitaModel` 只下载当前画质。新模型加载完成前继续显示旧模型，切换后释放旧模型的几何、材质、贴图、图像位图、骨骼纹理和动画绑定。连续切换时，取消已不需要的下载。场景中的宠物位置和正在执行的行为随切换延续。

重新导出时，可将贴图转为 WebP 后用 `gltfpack` 0.25 压缩，使用 `-cc -kn -km -kv -vpf -vp 16 -vt 14 -vn 10 -at 22 -ar 16 -as 22 -af 0 -ac`。浮点位置保留网格绑定姿态的坐标基准，触摸判定会直接读取这些坐标。

- `Idle_1` 用于待机，`Idle_2` 用于呼唤和摸背后回头，`Idle_3` 用于摸头。待机时从当前蒙皮姿态取爪底最低点，平滑校准站立高度。耳朵、脸颊、颈侧和腰部的反应叠加在待机或坐姿上。摸背时按触碰一侧选用 `Idle_2` 的转头方向。
- 心情达到 65 时，清醒的团子会在站立待机和自主步行中叠加短暂的摇尾。每次随机选两到三下和不同的节奏与幅度，较高的心情和活泼性格会缩短间隔。坐下、摸尾巴、侧躺、休息、等待球停稳或追球时平滑让位给当前动作。试玩使用示例心情 78，登录后使用服务端心情。
- 抚摸根据实际命中点的绑定姿态坐标与插值后的蒙皮权重，区分头顶、耳朵、脸颊、下巴、胸颈、肩背、腰臀、腿爪、尾巴和腹部。腿和爪的反应区分左右与前后，尾根摇尾，尾尖轻摆。手机触控中心落在轮廓外时，可命中 10 CSS 像素内最近的可见表面。按住滑出范围时，手会短暂保留接触姿势。梳毛从背部按下，沿肩背朝尾巴方向拖动一段距离后结算，团子会摇尾回应。一次按下最多结算一次梳毛。

- 按住拖到另一个部位并抚过一小段后，团子会接上该部位的反应。一次按下只结算一次抚摸，拖动中的后续反应只在客户端播放。
- 玩家手跟随动画中的宠物表面。点按头或背时轻抚一次，按住时掌心贴近，拖动时手腕随移动方向微调。挠下巴时掌心朝上，食指与中指错开弯曲，两个指腹平滑换力。摸背时手腕沿背部曲面转动，让掌心靠近，正面摸头时缩短袖口遮挡。拇指随姿势收拢。梳毛时保持握姿，以梳齿贴合背部。
- 切换部位时平滑过渡手的位置、手腕角度和指节。短暂扫过部位边缘时保持当前手势。团子转动后会尝试重新取得指针下的接触点，短暂失去接触时保留手势，离开后收手并淡出。用当前姿态的网格检查手指、手掌、袖口和梳子与犬身的间距，所有模型共用场景深度缓冲。右手 GLB 保留 16 根骨骼，减面后约 3,600 个三角形，在项目内加载。[Innerscene 右手模型](https://www.innerscene.com/tools/library/3d-parts/posable-anatomical-right-hand-f6098b4f) · [CC0 1.0](https://creativecommons.org/publicdomain/zero/1.0/)
- 呼唤时先转向玩家，然后沿安全路线回到房间前场，面向玩家等候。前方被挡住时会停在安全处回应。
- 玩家手和球共用场景深度。球裸露的轮廓外保留少量指针容差，直接命中犬身时按首个交点处理。按住球期间捕获指针。拇指从侧面贴球，其他四指从另一侧收拢，球靠近掌心并在收拢后抬起随手移动。拖动方向和长度给松手的球一个初速度，手指张开并随挥。轻点或指针取消时，手把球放回原处。

- 球停稳后团子才开始追球，用 `Run_F_IP` 和对应的根运动步幅移动，靠近球时减速步行。低头和抬头复用 `EatDrink_start`、`EatDrink_end`，在嘴碰到球的高度衔接，叼住后球随头部骨骼移动。返回用步行动画，团子会在房间前侧放下球。

### 11.3 犬种资源验收

每个犬种接入时执行同一套资源与运行验收：

- GLB 能在目标浏览器加载，高低画质资源均能正常显示。
- 根骨骼方向、模型缩放、脚底高度和碰撞范围正确。
- 必需语义骨骼均有映射；可选骨骼缺失时使用配置的替代策略。
- 基础动作语义均有有效动画映射或明确回退；关键动作不能出现 T-pose、脚底滑动或动作中断。
- 触摸检测能区分主要身体区域，手部模型不会明显穿透或悬空。
- 进食、喝水、追球、叼球、移动和休息使用该犬种自己的体型参数。
- 犬种专属动作和声音只在该犬种能力表声明后触发。

## 12. 测试策略

- 单元测试：时间结算、状态边界、性格参数、互动效果、犬种行为倾向和动作映射。
- 资源契约测试：每个犬种的必需动作、骨骼映射、触摸区域和体型参数完整性。
- 跨犬种回归：同一套抚摸、呼唤、喂食、玩耍、梳毛和自主行为用例在所有已开放犬种执行。
- 数据库集成测试：注册登录、事务、幂等、并发版本。
- API 测试：权限隔离、输入校验、错误响应。
- 前端测试：互动工具、状态展示、同步状态。
- Playwright E2E：注册、领养、互动、退出、另一设备重新登录。
- 时间测试使用可注入的服务端 Clock，不修改操作系统时间。

关键验收场景：
- 同一账号两个客户端同时喂食，物品不能重复扣除。
- 页面离线数小时后，状态按服务端时间结算。
- 客户端修改系统时间，结算结果不变。
- API 失败时不显示虚假的已保存状态。
- 一个用户无法读取或修改另一个用户的宠物。
- 新增犬种配置后，现有犬种的模型、动作和互动不回退。
- 缺少可选骨骼或非关键动画片段时，适配层按配置回退并记录诊断信息。
- 通用互动组件不直接引用具体犬种的骨骼名和动画片段名。

## 13. 可观测性与备份

- 应用日志输出到 journald。
- 日志包含 requestId、路由、耗时和错误类别，不记录密码、Cookie 或原始 Session。
- SQLite 使用 WAL。
- 备份使用 SQLite 在线备份机制或一致性快照，不直接复制正在写入的数据库主文件。
- 备份放在独立目录，设置保留周期，并定期进行恢复演练。
